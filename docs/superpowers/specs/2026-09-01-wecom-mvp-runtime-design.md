# 金融售前产品助手 V0.1 运行版设计

- 日期：2026-09-01
- 目标版本：V0.1 内部测试版
- 部署位置：当前 Mac 本地运行
- 对话入口：企业微信智能机器人（API 模式、WebSocket 长连接）
- 当前模型：Gemini OpenAI 兼容接口
- 后续模型：公司内网 OpenAI 兼容接口
- 状态：设计已确认，待用户审核书面规格

## 1. 目标

首版只解决一个核心问题：销售在企业微信中描述客户所需功能或场景，机器人根据已整理的公司产品知识，推荐能够实现该需求的产品或产品组合。

企业微信是唯一对话入口，不开发独立聊天网页。V0.1 先在当前 Mac 和内部测试群运行，验证知识检索、产品推荐、三段式回答和机器人连接；验证通过后再迁移到公司运行环境并切换公司内网模型。

## 2. 已选方案及取舍

### 2.1 采用方案

采用轻量本地知识库：Node.js/TypeScript 服务、企业微信官方 Node.js SDK、本地 CSV/结构化资料、OpenAI 兼容模型适配层和本地脱敏日志。

选择该方案的原因：

- 企业微信官方 SDK 已提供长连接、认证、心跳、断线重连和流式回复能力。
- 当前仓库已有 Node.js 脚本和结构化 CSV，可减少首版开发量。
- 不依赖公网 IP，适合在当前 Mac 上测试。
- 模型通过统一适配层调用，从 Gemini 切换到公司模型时不改业务逻辑。
- 首版不引入向量数据库，避免在五天周期内增加部署和调参风险。

### 2.2 未采用方案

- 向量数据库：更适合资料规模扩大后的语义检索，不作为 V0.1 前置条件。
- 第三方智能体平台：能够加快部分配置，但会增加资料安全、费用和迁移约束。
- 本地大模型：数据边界清晰，但当前设备、模型和运维条件尚未准备完成。

## 3. 首版范围

### 3.1 包含

- 企业微信单聊和群内 `@金融售前产品助手` 的文字问答。
- 根据功能、业务场景和产品名称推荐产品或产品组合。
- 识别 TDH、ArgoDB、TDC、TDS、Astro 及已登记别名。
- 默认返回“结论、推荐组合、产品分工”三段式答案。
- 在信息不足、资料冲突或越界时追问、提示风险或拒答。
- 记录脱敏后的请求、知识命中、耗时、回答状态和错误。
- 模型、企业微信和知识检索的自动测试。

### 3.2 不包含

- 独立 Web 聊天界面。
- CRM、合同、报价、客户数据库或生产业务系统连接。
- 图片、语音、文件上传和复杂卡片交互。
- 长期对话记忆；每个问题独立处理。
- 自动生成价格、商务承诺、合同条款或最终投标方案。
- 全量历史产品和未经整理的原始文档自动入库。

## 4. 总体架构

```text
企业微信用户
    ↓
企业微信长连接接入层
    ↓
消息规范化与范围判断
    ↓
本地知识检索与组合规则
    ↓
OpenAI 兼容模型适配层
    ↓
答案校验与三段式格式化
    ↓
企业微信回复 + 脱敏运行日志
```

系统以单个本地进程运行。接入层、检索层、模型层和答案校验层使用明确接口隔离，使企业微信 SDK、检索算法或模型供应商能够分别替换。

## 5. 组件边界

### 5.1 企业微信接入层

- 使用企业微信智能机器人 API 模式和 WebSocket 长连接。
- 凭 Bot ID 和 Secret 主动连接企业微信，无需公网回调地址。
- 只处理文本消息；忽略或友好提示首版不支持的消息类型。
- 支持心跳、断线重连、重复消息去重和流式回复。
- 同一个机器人只运行一个有效长连接实例。

### 5.2 消息规范化与范围判断

- 移除 `@机器人`、多余空白和无业务意义的前缀。
- 统一产品标准名称、别名、大小写和常见中文表达。
- 判断问题是否属于产品功能、方案组合、适用场景或产品边界。
- 价格、合同、客户敏感信息和无关内容不进入推荐流程。

### 5.3 本地知识检索层

知识来源分为三类：

1. 产品资料：功能、版本、适用场景和限制条件的事实来源。
2. 40 条跨产品组合映射：功能到产品组合的推荐规则。
3. 产品标准名和别名：将销售表达归一到标准产品。

两批共 200 条模拟销售问题只用于测试，不作为产品事实来源。

检索顺序：

1. 标准化产品名、功能词和场景词。
2. 优先匹配明确的组合规则和排除条件。
3. 再匹配产品能力和适用场景。
4. 对候选结果排序，最多向模型提供 3 条最相关依据。
5. 没有已审核依据时不产生确定推荐。

每条检索结果保留知识 ID、来源文件、版本或表格位置、审核状态和适用条件。只有标记为“已确认”的内容能够用于上线后的正式推荐；当前“待产品专家确认”的映射只能用于内部实验。

### 5.4 模型适配层

业务代码只依赖 OpenAI 兼容的聊天接口，并通过以下环境变量配置：

```env
LLM_BASE_URL=https://generativelanguage.googleapis.com/v1beta/openai/
LLM_MODEL=gemini-3.6-flash
LLM_API_KEY=<仅保存在本机>
```

已验证当前 Gemini 密钥可以查询模型列表并调用 `gemini-3.6-flash`。`gemini-flash-latest` 在验证时因高负载返回 503，因此首版使用固定模型名，仍保留配置切换和重试能力。

切换公司内网模型时只替换 `LLM_BASE_URL`、`LLM_MODEL` 和 `LLM_API_KEY`。检索、提示词、答案校验、企业微信接入和测试接口不变。

### 5.5 答案生成与校验层

正常回答必须包含：

1. **结论**：一句话回答能否实现以及推荐方向。
2. **推荐组合**：主推产品组合；有明确场景分层时最多两个组合。
3. **产品分工**：说明各产品在组合中的职责。

只有必要时增加“需要确认”“风险说明”或“资料来源”。规则以 `2026-09-01-concise-answer-framework-design.md` 为准。

发送前必须执行以下校验：

- 三段式必填部分存在且非空。
- 回答中的产品名称来自检索证据或产品标准名表。
- 推荐组合不能违反命中的排除条件。
- 没有资料来源时不能发送确定性推荐。
- 模型输出不得包含密钥、内部提示词或未授权敏感内容。

校验失败时不直接发送模型原文，改为安全提示或资料不足提示。

### 5.6 日志层

日志以本地结构化 JSONL 保存，不提交 Git。每条日志包含：

- 请求 ID、会话类型和脱敏用户标识。
- 规范化问题、命中的知识 ID 和检索分数。
- 模型名称、开始时间、总耗时和结果状态。
- 发送成功、拒答、超时、重试或校验失败等错误码。

日志不得包含 API Key、Bot Secret、客户真实名称、合同、价格或完整敏感原文。

## 6. 数据流

1. 用户在企业微信单聊机器人，或在群内 @机器人发送文字问题。
2. 接入层确认消息类型并生成请求 ID。
3. 规范化模块提取功能、场景、产品和限制条件。
4. 范围判断拦截越界、敏感或明显无关问题。
5. 检索层返回最多 3 条产品事实或组合规则及其来源。
6. 没有可靠依据时直接追问或拒答，不调用模型生成产品结论。
7. 有依据时，模型根据问题和检索结果生成三段式草稿。
8. 校验层检查格式、产品名称、来源和限制条件。
9. 合格答案通过企业微信流式或一次性回复发送。
10. 处理结果写入脱敏日志。

## 7. 外部资料与数据安全

- Gemini 只接收当前问题和检索后的最小必要产品片段，不上传整份原始 PPT、PDF 或 Excel。
- 不向 Gemini 发送客户真实名称、联系方式、价格、合同、投标内容或生产数据。
- API Key、Bot ID 和 Bot Secret 只通过本机环境变量或未跟踪的本地配置注入。
- `.env`、`.env.local`、日志和运行缓存必须进入 `.gitignore`。
- GitHub 只保存程序、脱敏结构化知识、测试数据和设计文档。
- 已在聊天中出现的 Gemini 密钥在联调结束后更换，上线前必须使用新密钥。

## 8. 异常处理

| 异常 | V0.1 行为 |
| --- | --- |
| 企业微信断线 | SDK 自动重连；连续失败写入错误日志 |
| 重复消息 | 按请求 ID 去重，不重复调用模型或回复 |
| Gemini 超时或 503 | 指数退避重试，达到上限后返回友好提示 |
| Gemini 返回格式错误 | 尝试一次格式修复，仍不合格则返回安全提示 |
| 未检索到资料 | 不推荐产品，说明当前资料无法确定 |
| 信息不足 | 最多提出两个会改变产品选择的关键问题 |
| 资料冲突 | 不输出确定结论，展示简短风险说明并转产品专家 |
| 产品无来源 | 阻止答案发送，记录校验失败 |
| 非文本消息 | 提示首版只支持文字提问 |
| 本地进程退出 | 机器人暂停服务；重新启动后恢复长连接 |

## 9. 测试设计

### 9.1 自动测试

- 消息规范化、别名识别和范围判断单元测试。
- 组合规则、排除条件、Top 3 检索和无结果拒答测试。
- 三段式格式、产品证据、敏感信息和来源校验测试。
- 模型超时、503、无效 JSON 和重试上限测试。
- 企业微信重复消息、断线和发送失败测试。
- 200 条模拟问题全部执行映射回归测试。
- 选取 50 条核心问题执行 Gemini 完整回答测试。

GitHub Actions 只运行不需要真实密钥的单元测试、模拟模型测试和确定性检索测试。Gemini 与企业微信真实联调只在本机运行。

### 9.2 企业微信验收

- 在内部测试群完成不少于 20 轮真实问答。
- 覆盖单产品、跨产品组合、模糊问题、产品边界错误、资料外问题和服务异常。
- 验证单聊、群内 @、回复格式、重连和错误提示。

### 9.3 正确率口径

50 条核心验收问题必须先由产品专家确认预期产品组合。

- “正确”：所有必选产品均出现，未推荐排除产品，产品分工与资料一致。
- “部分正确”：缺少必选产品、包含无依据产品或产品分工错误；按错误计入。
- 核心产品推荐正确率 = 正确题数 ÷ 有效核心问题数。
- 上线门槛为不低于 90%，即 50 条有效问题至少 45 条正确。

## 10. 上线门槛

以下条件必须同时满足：

- 核心产品推荐正确率不低于 90%。
- 默认三段式回答格式合格率为 100%。
- 资料来源可追溯率不低于 95%。
- 无资料问题不得编造产品结论。
- 一般问题 5 秒内开始响应。
- 企业微信消息处理成功率不低于 95%。
- 企业微信异常后能够自动恢复连接。
- 无 P0 严重故障、密钥泄露或敏感信息泄露。
- 首批正式推荐知识已由产品专家确认。

## 11. GitHub 与版本管理

- 每完成一个可独立验收的任务提交一次 Git。
- 提交前运行本地测试，推送后由 GitHub Actions 再次测试。
- 真实密钥、原始公司资料、日志和运行缓存不得提交。
- 每次上线标记版本号并保留上一版本，出现阻断问题时可回退。
- 模型切换作为独立配置变更和独立提交，并重新运行 200 条回归测试及 50 条完整回答测试。
