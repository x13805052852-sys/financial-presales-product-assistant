# 企业微信单轮上下文识别设计

## 1. 背景

当前金融售前产品助手将企业微信中的每条文字消息作为独立问题处理。用户发送“所以正常能到多少”“那这个适合银行吗”等省略主语的自然追问时，系统不会读取上一轮问题和答案，只会根据当前文字重新检索，因此可能扩大推荐范围或偏离上一轮已经确定的产品组合。

销售人员不应学习“新问题”“继续追问”等特殊口令。本功能需要在不改变自然提问习惯的前提下，自动识别同一销售是在追问上一轮，还是开始一个新的产品问题。

## 2. 目标与验收标准

### 2.1 目标

- 自动识别同一销售紧邻上一轮的自然追问。
- 群聊中按提问人隔离上下文，不继承其他销售的问题。
- 只保留一轮上下文，降低旧需求污染新问题的风险。
- 上下文只用于补全检索问题，不作为产品能力证据。
- 上下文识别不依赖具体大模型，后续切换 DeepSeek 时保持一致行为。
- 判断不清时按新问题处理，优先避免错误继承。

### 2.2 验收标准

- 100 组双轮测试的上下文判断正确率不低于 95%。
- 错误继承率不高于 2%。
- 200 条原有单轮问题的核心产品推荐正确率不低于 90%。
- 更换模型供应商后，必须重新运行 200 条单轮问题和 100 组双轮问题。
- 不同销售在同一群聊中连续提问时，不得发生上下文串话。

## 3. 范围

### 3.1 首版包含

- 企业微信单聊和群聊文字消息。
- 同一用户紧邻上一轮的上下文识别。
- 企业微信引用消息识别。
- 一轮内存上下文、30 分钟失效和容量控制。
- 回答中的简短追问提示。
- 上下文判断、消息隔离和回归测试。

### 3.2 首版不包含

- 两轮以上的长期会话记忆。
- 跨群聊或跨单聊继承上下文。
- 将聊天上下文写入数据库、Excel 或 Git。
- 依靠大模型自由判断追问关系。
- 从其他销售的消息继承上下文。
- 机器人重启后恢复历史上下文。

## 4. 核心原则

1. **同群同人**：群聊使用群 ID 和发送人 ID 共同隔离；单聊使用发送人 ID 隔离。
2. **只看上一轮**：每次回答后用当前轮覆盖旧记录，不形成无限聊天历史。
3. **规则判定**：程序根据引用、承接词、主语省略、实体重合和完整性进行评分，不调用 GLM 或 DeepSeek 做追问分类。
4. **保守回退**：只有达到明确阈值才继承，任何异常或不确定结果都按新问题处理。
5. **证据重新检索**：继承的内容只补全查询；最终结论仍必须由知识库证据支持。
6. **用户可感知**：发生继承时，在回答前显示一行简短提示，便于销售发现误判。

## 5. 组件设计

### 5.1 会话键生成器

企业微信文字消息提供 `chattype`、`chatid` 和 `from.userid`。系统按以下方式生成会话键：

- 群聊：`group | chatid | userid`
- 单聊：`single | userid`

运行时将组合值计算为 SHA-256 摘要后作为内存索引。原始群 ID 和用户 ID 不进入业务日志。不同用户即使位于同一个群，也不会读取彼此的上下文。

### 5.2 单轮上下文仓库

上下文保存在当前机器人进程的有界内存 Map 中，每个会话键最多保存一条 `ContextSnapshot`：

```ts
interface ContextSnapshot {
  sessionKeyHash: string;
  messageId: string;
  question: string;
  resolvedQuestion: string;
  intent: string;
  products: string[];
  capabilities: string[];
  knowledgeIds: string[];
  answerSummary: string;
  status: "answered" | "retryable_error";
  createdAt: number;
}
```

- 保存时间为30分钟，读取时惰性删除过期记录。
- 容量上限为 1,000 个会话；超过上限时删除最早记录。
- 内容只存在内存中，机器人重启后自动清空。
- 正常回答后写入当前轮并覆盖旧记录。
- 可重试错误保留当前问题，使“再试一下”能够重新执行失败的问题。
- 敏感、越界或被拒绝的问题不写入上下文。

### 5.3 上下文判定器

判定器先执行硬性门槛，再计算追问分数。

#### 硬性门槛

以下任一条件成立时直接按新问题处理：

- 当前会话键没有上一轮记录。
- 上一轮已超过30分钟。
- 消息来自不同的群或不同的用户。
- 当前问题触发敏感或越界拦截。

#### 追问信号

| 信号 | 分数 | 示例 |
| --- | ---: | --- |
| 引用内容与上一问或上一答匹配 | +4 | 引用机器人上一条回答继续提问 |
| 明确承接词或重试表达 | +3 | 所以、那、这个、它、为什么、再试一下 |
| 省略产品或场景主语 | +2 | “正常能到多少？”“银行能用吗？” |
| 产品、能力或场景与上一轮重合 | +2 | 两轮均涉及实时治理或 ArgoDB |
| 5分钟内紧邻提问 | +1 | 只作为弱信号，不能单独触发继承 |

#### 新话题信号

| 信号 | 分数 | 示例 |
| --- | ---: | --- |
| 当前问题完整描述了独立需求，且与上一轮实体不同 | -4 | 上一轮问实时治理，当前问 Astro 更新功能 |
| 当前问题明确指定了与上一轮不同的产品或业务场景 | -3 | 从 ArgoDB 切换为完全独立的 TDH 升级问题 |
| 当前问题与上一轮没有实体、能力或场景重合 | -2 | 无任何可解释的承接关系 |

总分达到 4 分时判定为追问，否则按新问题处理。硬性门槛的优先级高于分数。规则异常、字段缺失或计算失败时统一按新问题处理。

### 5.4 问题补全器

判定为追问后，不把上一轮完整答案直接拼入模型提示词。问题补全器仅使用结构化摘要生成内部检索问题：

```text
上一轮客户需求：需要数据治理，并要求实时流动达到毫秒级
上一轮推荐组合：Slipstream + ArgoDB AP + TDS-SUITE-D
当前追问：所以正常能到多少？
补全问题：针对上述组合，现有知识资料能够支持的正常实时级别是多少？
```

补全结果需再次执行范围判断。知识检索、回答框架分类和答案生成使用补全后的问题，产品事实仍必须来自重新命中的知识条目。上一轮答案中的自然语言结论不能直接成为证据。

### 5.5 回答提示

模型回答通过现有格式和证据校验后，由消息层在最前面增加：

```text
承接上一问：毫秒级实时治理
```

该提示由程序生成，不属于模型输出，也不参与动态回答框架的标题校验。摘要控制在20个中文字符以内，不包含客户名称、价格、合同或其他敏感内容。

## 6. 处理流程

1. 企业微信接收文字消息并读取消息 ID、会话类型、群 ID、发送人 ID 和引用内容。
2. 先对当前原始问题执行敏感与越界判断。
3. 计算会话键并读取同群同人的上一轮快照。
4. 上下文判定器执行硬性门槛和规则评分。
5. 若为追问，问题补全器生成内部完整问题；否则直接使用当前问题。
6. 对补全后的问题再次执行范围判断。
7. 使用补全问题完成意图分类、知识检索、模型回答和答案校验。
8. 若继承成功，在已校验答案前添加简短提示。
9. 根据结果保存或覆盖当前会话的一轮上下文。
10. 审计日志记录是否继承、规则命中项和分数，但不记录真实群 ID、用户 ID或完整敏感原文。

## 7. 错误处理与安全

- 上下文仓库不可用、记录损坏或判定器抛错时，按新问题继续处理，不影响基本问答。
- 引用消息无法与上一轮匹配时，不能仅凭“存在引用”强制继承。
- 当前问题与上一轮产品组合冲突时，不继承上一轮推荐。
- 发生追问误判时，回答开头的“承接上一问”提示帮助用户立即发现。
- 补全问题没有重新命中可靠资料时，使用现有的资料不足提示，不生成确定性推荐。
- 上下文数据不落盘、不提交 Git、不写入普通日志。
- 大模型只能接收已经结构化和最小化的上下文摘要。

## 8. 测试设计

### 8.1 100 组双轮测试集

- 40 组正常追问：承接词、代词、省略主语、参数追问、原因追问和边界追问。
- 30 组同一销售换话题：完整新需求、不同产品、不同客户场景和相同产品的独立问题。
- 15 组群内交叉提问：不同销售紧邻提问、相互引用和同一关键词干扰。
- 15 组困难样例：引用不匹配、仅有“呢”、短问题、重试、超时和超过30分钟。

每组记录期望结果、实际结果、命中规则、分数、是否继承、补全问题和最终产品推荐。

### 8.2 自动化测试

- 会话键隔离：同群不同人、同人不同群和单聊分别验证。
- TTL 与容量：30分钟失效、覆盖上一轮和 1,000 会话淘汰。
- 规则判定：每项正负信号、阈值边界和默认新问题。
- 引用处理：匹配上一轮、引用其他消息和字段缺失。
- 安全处理：敏感问题不写入上下文，补全后再次拦截。
- 消息集成：追问提示只在实际继承时出现。
- 回归测试：现有 32 项程序测试、200 条单轮问题和仓库质量测试保持通过。

### 8.3 DeepSeek 切换验证

上下文判定器不调用模型，因此更换 DeepSeek 不改变追问分类结果。模型切换后仍需验证：

- OpenAI 兼容适配是否正常。
- 三种动态回答框架是否继续满足格式要求。
- 200 条单轮问题的推荐正确率。
- 100 组双轮问题在补全后的推荐正确率。
- 超时、重试和模型失败时是否仍返回安全提示。

## 9. 示例

### 9.1 自动追问

上一问：

```text
客户需要数据治理并要求实时流动达到毫秒级，应该怎么搭配？
```

当前问：

```text
所以正常能到多少？
```

判定结果：同群同人、承接词、主语省略且能力重合，总分达到阈值，继承上一轮。

### 9.2 自动开始新问题

上一问讨论实时数据治理，当前问：

```text
Astro目前更新了哪些主要功能？
```

判定结果：当前问题完整、产品和意图均发生变化，按新问题处理并覆盖旧上下文。

### 9.3 群聊用户隔离

销售 A 问完实时治理后，销售 B 发送：

```text
那正常能到多少？
```

判定结果：发送人不同，硬性门槛不通过，不读取销售 A 的上下文。

## 10. 上线与观察

- 首次只在内部测试群启用。
- 日志增加 `contextDecision`、`contextScore` 和脱敏后的规则命中项。
- 每次误判记录为双轮错题，补充到 100 组测试集后再调整规则。
- 调整分数或阈值时必须重新运行全部双轮测试，避免为了修复一个样例破坏其他场景。
- 达到上下文正确率、错误继承率和产品推荐正确率门槛后，再进入更大范围灰度。
