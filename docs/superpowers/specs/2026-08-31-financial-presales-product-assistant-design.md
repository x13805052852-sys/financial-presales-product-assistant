# 金融售前产品匹配助手设计

- 日期：2026-08-31
- 目标版本：内部试运行 V1.0
- 计划周期：5 个工作日
- 上线方式：第 5 天在企业微信内部销售群灰度上线

## 1. 背景与目标

销售面对客户需求时，需要快速判断“哪个功能由哪个产品实现、为什么推荐、需要哪些前提”。现有知识分散在产品 Excel、PPT、PDF 和个人经验中，检索成本高，且容易出现产品名称、版本和推荐口径不一致。

首版助手的目标是将客户需求转换为标准化的产品推荐，并给出可追溯的资料依据。它是销售决策辅助工具，不替代产品专家完成最终方案评审。

## 2. 用户与使用场景

主要用户：公司内部销售、售前顾问和产品专家。

核心场景：

1. 销售描述客户需要的功能，助手推荐对应产品。
2. 销售描述客户现有技术栈，助手推荐替代或升级路径。
3. 销售询问两个产品的适用场景差异。
4. 销售询问某方案需要哪些产品组合。
5. 助手在资料不足时说明缺少的信息，并提示向产品专家确认。

## 3. 首版范围

### 3.1 包含

- 企业微信内部群内通过 `@金融售前助手 + 问题` 发起问答。
- 识别客户需求、业务场景、现有系统和关键限制条件。
- 从已审核知识库中匹配产品或产品组合。
- 展示推荐理由、适用条件、可选方案和资料来源。
- 支持与当前问题相关的短上下文追问。
- 记录问题、检索来源、响应时长、回答结果和异常。
- 对资料外、敏感或无法确认的问题安全拒答。

### 3.2 不包含

- 不连接 CRM、合同、报价、客户名单或生产数据库。
- 不生成价格、商务承诺、合同条款或最终投标方案。
- 不面向外部客户群开放。
- 不在首版覆盖所有长尾产品和历史版本。
- 不允许模型基于公开互联网自行补充公司产品结论。

## 4. 首批产品范围

首批候选为以下 8 组产品线：

| 产品线 | 首版主要匹配场景 |
| --- | --- |
| TDH | 湖仓一体、数据湖、数据仓库、大数据平台替代与升级 |
| ArgoDB | HTAP、Oracle/HANA 替代、实时分析 |
| TDC | 多集群管理、数据服务和 AI 算力服务 |
| TDS / Astro | 智能数据中台、数据治理和数据安全 |
| LLMOps | 大模型管理、Agent 构建和算力管理 |
| TKH | 知识工程、非结构化数据管理和 AI-ready Data Platform |
| 无涯·问数 / 无涯·问知 | 自然语言问数、分析报告和知识问答 |
| Scope | Elasticsearch 信创替代 |

纳入首版的必要条件：至少有一份有效且已确认的产品资料、产品专家能够确认推荐口径、至少有两条真实销售需求用于验收。

## 5. 知识模型

每条知识必须归入以下结构：

`客户需求 → 功能能力 → 解决方案 → 推荐产品组合 → 产品版本 → 适用条件 → 限制条件 → 资料来源`

关键字段：

- 客户需求：销售或客户的自然语言表达。
- 标准功能：统一后的功能名称，例如“实时湖仓”“多集群纳管”。
- 解决方案：对外售前方案名称。
- 主推产品：首选产品或组合。
- 可选产品：满足特定条件时采用的替代组合。
- 触发条件：客户现有平台、数据类型、部署方式和性能要求。
- 排除条件：不适用场景和必须人工确认的情况。
- 来源：文件名、版本、发布日期、页码或表格行号。
- 审核状态：仅“已确认”内容能够用于正式推荐。

## 6. 回答规范

机器人默认采用三段式简洁回答：

1. **结论**：一句话回答能否实现以及推荐方向。
2. **推荐组合**：展示主推产品组合；存在明显场景分层时最多展示两个组合。
3. **产品分工**：简要说明各产品分别负责什么。

完整的推荐理由、适用条件、可选方案、需确认信息和资料来源继续保留在知识库中。只有信息不足、资料冲突、安全越界或用户主动要求详细说明时，才按需增加；需确认信息最多两个问题。具体规范见 `2026-09-01-concise-answer-framework-design.md`。

禁止行为：

- 不得虚构产品能力、版本、案例或客户名称。
- 不得把内部推测写成确定结论。
- 不得输出资料中标记为禁止传播的内容。
- 不得提供价格、折扣和未经授权的商务承诺。

## 7. 逻辑组件

1. **企业微信接入层**：接收群内被 @ 的消息，维护连接并发送流式回复。
2. **问题理解层**：提取客户需求、现有环境、目标能力和限制条件。
3. **知识检索层**：按产品、方案、版本和场景检索已审核资料，并对结果排序。
4. **产品匹配层**：结合映射规则与检索证据生成推荐候选。
5. **回答生成层**：按照固定格式生成答案，并附带来源。
6. **安全控制层**：处理资料不足、越权、提示词攻击和敏感内容。
7. **日志与反馈层**：记录问题、答案、来源、耗时和人工反馈，用于持续修正。

## 8. 数据流

1. 用户在内部群中 @机器人并描述客户需求。
2. 接入层收到消息，向用户展示正在处理状态。
3. 问题理解层提取标准功能和必要约束。
4. 知识检索层召回相关产品资料和映射规则。
5. 产品匹配层检查证据是否足以支持推荐。
6. 证据充分时生成结构化推荐；证据不足时返回需补充的信息或拒答。
7. 回复发送到原群聊，同时写入脱敏后的运行日志。

## 9. 异常处理

| 异常 | 处理方式 |
| --- | --- |
| 企业微信连接中断 | 自动重连；连续失败时通知维护人 |
| 模型或知识库超时 | 一次自动重试；仍失败则返回友好提示 |
| 未检索到资料 | 不推荐产品，提示当前知识库暂无依据 |
| 多份资料内容冲突 | 优先使用已审批的最新版本，并提示存在版本差异 |
| 问题缺少关键信息 | 最多提出两个澄清问题 |
| 涉及敏感或越权内容 | 拒绝回答并记录安全事件 |
| 生成答案没有来源 | 阻止正式推荐，改为资料不足提示 |

## 10. 测试与上线门槛

上线前使用 50 道验收问题，覆盖能力匹配、方案组合、产品比较、版本差异、模糊需求、资料外问题和安全问题。

必须同时满足：

- 核心问题推荐正确率不低于 90%。
- 回答来源可追溯率不低于 95%。
- 无资料问题不编造产品结论。
- 一般问题 5 秒内开始响应。
- 消息处理成功率不低于 95%。
- 无 P0 严重故障或敏感信息泄露。

## 11. 灰度与运维

第 5 天上午将版本发布到 10～20 人内部测试群。观察错误答案、消息失败、响应时间和用户反馈；修复阻断问题后再扩大可见范围。

上线后保留以下机制：

- 错题清单：记录错误推荐、缺失知识和原因。
- 资料更新登记：所有新增资料记录版本、来源和审核人。
- 每日复盘：上线后一周每天检查高频问题和异常答案。
- 回滚：保留上一版提示词、知识索引和运行配置。

## 12. 角色与责任

| 角色 | 责任 |
| --- | --- |
| 项目负责人 | 范围、进度、风险和上线决策 |
| 产品专家 | 产品口径、映射关系和验收答案确认 |
| AI/后端开发 | 知识库、智能体逻辑、企微接入和日志 |
| 企业微信管理员 | 创建机器人、权限、可见范围和凭证 |
| 销售测试用户 | 提供真实需求、试用并反馈问题 |

同一成员可以兼任多个角色，但每项任务只能指定一个最终负责人。
