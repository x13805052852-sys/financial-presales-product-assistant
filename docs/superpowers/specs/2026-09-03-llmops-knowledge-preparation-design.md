# LLMOps 售前知识库首版准备设计

- 日期：2026-09-03
- 资料目录：`/Users/quanzhilongxiaojiaoqi/Desktop/星环科技/LLMops/`
- 使用场景：销售描述客户需要的功能或场景，助手推荐 LLMOps 产品、组件或组合
- 目标：复用 TDH 已验证流程，形成可运行、可追溯、可测试的 LLMOps 首版知识
- 上线门槛：核心产品推荐正确率不低于 90%
- 审核状态：内部实验口径，待产品专家确认后转为正式售前口径

## 1. 已确认的范围

本轮只准备 LLMOps 产品线的售前知识，不改动企业微信接入方式，也不重新设计回答框架。机器人继续使用已经确定的动态简洁框架：

- 功能介绍类：结论、主要功能、口径说明。
- 产品选型类：结论、推荐组合、产品分工。
- 风险追问类：冲突点、实际影响、销售口径。
- 资料不足时最多追加两个会改变推荐结果的问题；存在版本冲突、性能承诺或规划能力时追加风险说明。

原始 PPT、PDF、Excel、图片和视频只保留在公司资料目录，不上传 GitHub。GitHub 仅保存脱敏后的资料清单、产品映射、模拟问题、测试程序和进度记录。

## 2. 备选处理方式

### 方案 A：所有资料直接入库

优点是速度快、覆盖面大；缺点是 LLMOps 1.x、2.x、3.0 的名称和能力会混在一起，测试报告、规划页和宣传数字也可能被当成当前承诺。首版不采用。

### 方案 B：只使用一份最新介绍材料

优点是口径统一；缺点是 Agent Go、TokenFactory、AI Infra 等细分能力证据不足，不能支持销售追问。首版不采用。

### 方案 C：按证据等级分层入库

将当前版销售材料设为默认知识，将旧手册、混合版本架构、历史培训、案例和测试报告分别放入条件库、证据库或排除区。该方案在速度、覆盖度和幻觉风险之间最平衡，作为本轮实施方案。

## 3. 资料分层设计

### 3.1 A 类：默认售前知识

首版使用以下 5 份当前版资料：

1. `04产品介绍/LLMOps3 上新：企业内部的Agent Engineering 是什么？LLMOps是如何做的？—260716（范豪钧）.pdf`
2. `04产品介绍/LLMOps3：平台介绍-AI转型 .pptx`
3. `04产品介绍/LLMOps3：大模型时代下的AI中台.pptx`
4. `04产品介绍/LLMOps3：TokenFactory词元工厂.pptx`
5. `04产品介绍/LLMOps3：AgentGo 智能体平台.pptx`

这些资料用于回答产品定位、场景选型、组件分工和组合推荐。性能数字、客户案例、竞品评价和“唯一”“第一”等营销性表述不得直接进入默认答案。

### 3.2 B 类：条件知识

- `LLMOps技术架构图.pptx` 同时包含 V2.0、V1.4、V1.3 和历史备份，只能在明确版本后使用。
- `Sophon_LLMOps_User_Manual-llm-1.4.3.pdf` 是 1.4.3 版本手册，可用于旧版功能或操作追问，不得证明 3.0 当前能力。
- 当前发布会视频可作为内容复核材料；没有完成转写和核验前，不能单独支撑产品结论。
- 在线手册入口截图只证明存在帮助文档入口，不是功能事实来源。

### 3.3 C 类：历史与证据材料

- LLMOps 1.x、2.x 的介绍、培训、案例和旧手册只用于版本追溯。
- 测试报告和漏洞扫描结果只用于质量或安全举证，不参与普通产品推荐。
- 竞品对比材料单独受控，不能默认进入对客回答。
- 标注规划中、路线图或特定测试环境的数据不得改写成当前通用能力。

## 4. 产品模型

首版将 LLMOps 3.0 拆为五个产品域，并将组件归属显式化：

| 产品域 | 中文名称 | 主要职责 | 关键组件或能力 |
| --- | --- | --- | --- |
| Corpus Studio | 星解 | 多模态语料开发与管理 | 语料处理、增强、标注、评测 |
| Model Foundry | 星铸 | 模型训练、推理与算力运营 | 模型生命周期、评测发布、TokenFactory |
| Knowledge Lodge | 星典 | 知识工程与推理 | KB Agent、多索引、业务本体、检索增强 |
| Agent Go | 星将 | 智能体与应用开发及运营 | AgentBox、Agent Buddy、Agent Session Manager |
| AI Infra | — | 企业级 AI 基础设施与统一治理 | Catalog、Discover、空间、身份、权限、审计、观测 |

别名表需要保留旧名称，但必须标明版本。例如旧资料中的 Agent Go“星构”不能覆盖 3.0 当前资料使用的“星将”。TokenFactory 归属于 Model Foundry，不应被回答成与五个产品域平级的第六个产品。

## 5. 首版组合规则

| 销售场景 | 推荐组合 | 主要分工 |
| --- | --- | --- |
| 专家型数字员工 | Agent Go + Knowledge Lodge + AI Infra | Agent 开发与运营、知识支撑、统一资产与权限底座 |
| 知识库质量和治理升级 | Knowledge Lodge + AI Infra + Corpus Studio | 知识工程、资产治理、高质量语料生产 |
| 多模型统一服务、成本和 Token 效率治理 | Model Foundry + TokenFactory + AI Infra | 模型与算力管理、统一服务与路由、权限审计和观测 |
| 企业统一 AI 生产底座 | 五个产品域组合 | 贯通语料、模型、知识、Agent 和企业级基础设施 |
| Vibe Coding 与智能体开发 | Agent Go / AgentBox + AI Infra | 浏览器开发、工具与知识资产接入、运行治理 |

跨产品涉及 TDH、ArgoDB、TDS、Astro、TDC AI 服务时，本轮只建立“待确认边界”，没有明确资料证据不得自动推荐组合。

## 6. 交付物

1. LLMOps 全量资料清单：格式、版本、日期、页数或幻灯片数、哈希、提取状态、知识层级和风险。
2. 资料筛选报告：明确默认入库、条件入库、证据材料和排除材料。
3. 首版资料文件夹：只复制 5 份 A 类资料，仍保留在公司资料目录中。
4. 产品别名表：处理五个产品域、组件名、英文名和历史名称冲突。
5. 功能—产品映射：每条包含功能、推荐产品、组件、适用条件、限制、来源和审核状态。
6. 场景—组合映射：每条说明组合、产品分工、必须追问和排除条件。
7. 100 条 LLMOps 单轮销售模拟问题。
8. LLMOps 两轮上下文问题：验证同一群、同一发送人、只继承上一轮的规则。
9. 自动校验和回归测试：检查映射完整性、题库覆盖、产品归属、来源和上下文隔离。
10. 进度表、README、Git 提交和 GitHub 备份。

## 7. 检索与回答流程

1. 识别问题类型：功能介绍、产品选型或风险追问。
2. 解析明确产品、组件、能力、场景、版本和限制条件。
3. 用别名表归一名称，再检索功能映射和组合映射。
4. 按 A 类、B 类、C 类顺序决定证据是否允许进入答案。
5. 发现旧版、规划项、测试数字或资料冲突时降低置信度，并追加风险说明。
6. 两轮对话只在同一群、同一发送人且第二轮为明显追问时补全上一轮主题；最终产品结论仍必须重新命中 LLMOps 映射。
7. 没有可靠证据时回答“当前知识库暂无依据”，不使用模型常识补写公司能力。

## 8. 测试与验收

- 5 份核心资料均完成文本提取或视觉核验，来源可追溯。
- 别名和功能映射中不存在未知产品、空来源或未标版本的历史别名。
- 100 条单轮问题编号唯一、分类覆盖完整，每条都有期望产品或安全动作。
- 两轮问题覆盖有效追问、同人换题、跨用户和超时四类场景。
- 核心产品推荐正确率不低于 90%。
- 资料来源可追溯率不低于 95%。
- 规划能力、营销数字、历史功能和安全材料不会被默认检索为当前售前承诺。
- 全部自动测试通过，Git 工作区不包含原始公司材料和密钥后才允许推送。

## 9. 明确不做

- 不修改企业微信机器人接入和部署配置。
- 不把原始公司文件、客户信息、内部价格、API Key、BotID 或 Secret 提交到 GitHub。
- 不把 LLMOps 历史资料全部转成对外承诺。
- 不在没有产品专家确认时承诺具体性能提升、毫秒时延、并发规模、兼容范围或路线图日期。

## 10. 实施顺序

1. 固化资料清单和筛选结论。
2. 创建首版资料文件夹并复制 A 类资料。
3. 生成别名、功能和组合映射。
4. 生成单轮与两轮模拟问题。
5. 接入现有知识加载器和检索回归测试。
6. 更新进度表，运行全量测试，提交并推送 GitHub。
