# 跨产品组合映射与第二批 100 条模拟问题设计

- 日期：2026-09-01
- 数据性质：内部模拟测试数据
- 产品范围：TDH、ArgoDB、TDC、TDS、Astro
- 使用范围：金融售前产品匹配助手的组合推荐测试
- 审核状态：待产品专家确认

## 1. 背景与目标

第一批 100 条模拟问题主要验证“单项能力对应哪个产品”。实际销售问题经常同时包含实时接入、数据库、数据治理、集群管理和智能体等多个要求，例如：

> 我想知道带有实时流入数据库中的功能并且带有数据治理的产品应当是哪个搭配？

第二批测试集用于验证助手能否拆解复合需求，选择合理的产品组合，解释每个产品的分工，并在时效、目标数据库或治理范围不清时先追问再推荐。

## 2. 范围与边界

### 2.1 纳入范围

- TDH：数据湖、数据仓库、数据集市、湖仓集一体和相关数据组件。
- ArgoDB：AP、TP、HTAP 及实时分析、事务处理和事务分析混合场景。
- TDC：单集群或多集群、单租户或多租户、云原生资源与数据服务管理。
- TDS：数据集成与开发、数据治理与分类分级、实时湖仓工具、数据云开发与运营平台。
- Astro：数据开发、数据治理和数据智查相关智能体，以及 Pilot、API/MCP 和平台集成能力。

### 2.2 暂不纳入

- LLMOps、TKH、无涯·问数、无涯·问知等其他产品线。
- 价格、折扣、合同条款和未经授权的商务承诺。
- 未脱敏的客户名单、联系人、合同或项目细节。
- 只有视频标题或宣传性软文、没有正式资料支撑的确定性能力结论。

## 3. 交付物

### 3.1 跨产品组合映射

建立约 35～40 条可追溯的组合映射，字段为：

`销售复合需求 → 能力拆分 → 主推组合 → 产品分工 → 可选组合 → 适用条件 → 必须追问 → 排除条件 → 资料来源 → 审核状态`

每条映射必须明确各产品承担的角色，不能只列出产品名称。

### 3.2 第二批 100 条模拟问题

生成独立于第一批 TDH 题库的跨产品测试集。沿用第一批问题字段，并增加：

- 命中的组合映射。
- 产品分工是否完整。
- 是否存在版本冲突。
- 推荐置信度。

### 3.3 输出格式

- 仓库 CSV：用于版本管理和自动测试。
- 可编辑 Excel：包含第二批 100 条问题、组合映射、分类统计和使用说明。
- 生成程序与自动校验：用于后续修改后重新生成 Excel。

原始 PPT、PDF、视频和其他内部资料保留在本地，不上传 GitHub。GitHub 只保存脱敏后的映射、模拟问题、设计说明和生成程序。

## 4. 产品角色模型

| 产品 | 主要角色 | 不能默认承担的角色 |
| --- | --- | --- |
| TDH | 数据湖、数仓、集市、湖仓集和多模型数据平台 | 纯 OLTP、智能治理编排、跨集群管理平台 |
| ArgoDB | 实时 AP、强一致 OLTP、HTAP 数据库 | 海量多类型数据湖、数据治理工具集、集群管理平台 |
| TDC | 云原生底座、集群与租户管理、跨集群资源能力 | 业务数据存储引擎、数据治理执行工具 |
| TDS | 数据集成、开发、治理、分类分级、运营和实时同步工具 | TDH/ArgoDB 的存储与计算引擎、智能体规划平台 |
| Astro | 目标理解、任务规划、专业 Agent 协同、数据开发/治理/智查智能化 | 底层数据库、数据平台或治理工具的替代品 |

Astro 与 TDS、TDH 或 ArgoDB 的关系应描述为“智能规划和执行入口 + 平台工具 + 数据底座”，不得把 Astro 单独描述为完整数据库或数据平台。

## 5. 推荐流程

1. 从销售问题中提取多个业务目标、技术能力和限制条件。
2. 将复合需求拆分为接入、存储、计算、治理、管理和智能化等能力。
3. 为每项能力匹配候选产品，并检查产品角色是否重复、冲突或缺失。
4. 检查时效、工作负载、目标系统、治理范围、集群数量等关键信息。
5. 信息足以改变推荐结果时，最多提出两个关键追问。
6. 证据充分时默认输出结论、推荐组合和产品分工；其他内容按需追加。
7. 资料不足、版本冲突或涉及越界承诺时，降低置信度并明确说明。

默认回答结构：

1. 结论。
2. 推荐组合。
3. 产品分工。

信息不足时追加“需要确认”，资料冲突或越界时追加“风险说明”，用户主动询问依据时再展示资料来源。完整字段继续保留用于内部审核。具体规范见 `2026-09-01-concise-answer-framework-design.md`。

## 7. 资料选择与证据优先级

证据优先级从高到低：

1. 最新产品介绍、白皮书和销售版本资料。
2. 产品培训和正式解决方案。
3. 当前版本手册和经脱敏的最佳实践。
4. 历史版本、历史案例和旧版培训材料。
5. 视频标题和宣传软文只能用作发现线索，不能单独支撑确定性结论。

资料冲突时不得静默合并。映射需要保留冲突说明、涉及文件和待确认事项。

### 7.1 Astro 版本口径冲突

`Astro产品介绍-2026-v4.pptx`描述 12 个专业 Agent；`Astro白皮书-中文260717.pdf`描述 11 个标准垂域智能体，两者在资产标签、血缘分析等条目上存在版本差异。

处理规则：

- 按具体能力和 Agent 名称进行映射。
- 未经产品专家确认，不回答 Astro 标准 Agent 的确定总数。
- 涉及资产标签或血缘分析时，标记资料版本与冲突状态。
- 组合推荐不因数量冲突而否定已在正式材料中明确描述的具体能力。

## 8. 示例映射

### 销售问题

我想知道带有实时流入数据库中的功能并且带有数据治理的产品应当是哪个搭配？

### 能力拆分

- 数据实时接入或实时同步。
- 目标数据平台或数据库。
- 数据标准、质量、分类分级、目录等治理能力。
- 是否需要智能体自动规划和执行治理任务。

### 预期动作

先追问再推荐：

1. 实时要求是分钟级、秒级还是亚秒级，数据写入后是否立即分析？
2. 数据治理主要指标准、质量、分类分级、资产目录还是完整治理流程？

初步组合由答案决定：

- 分钟级湖仓与治理：TDH 相关 Edition + TDS 治理/实时工具；需要智能化治理时增加 Astro。
- 秒级或亚秒级实时分析与治理：ArgoDB AP + TDS 治理/实时工具；需要智能体协同时增加 Astro。
- 实时流式 ETL：按链路评估 Slipstream 或 TDS 实时湖仓工具中的 Flashsync/Midgard，不能只凭“实时流入”四个字确定产品。

所有具体组合均需在映射建设阶段根据版本、License 和正式资料进一步限定。

## 9. 异常与安全处理

| 情况 | 处理方式 |
| --- | --- |
| 多份资料冲突 | 展示冲突并降低置信度，等待产品专家确认 |
| 能力缺少证据 | 回答“当前资料不足”，不补写产品能力 |
| 信息不足 | 最多提出两个会改变推荐结果的问题 |
| 产品角色错误 | 先纠正前提，再给可选组合 |
| 价格、折扣或合同 | 拒绝确定性回答，转交有权限负责人 |
| 绝对性能、零停机或零丢失 | 要求基线、版本、拓扑和 PoC，不做绝对承诺 |
| 客户、合同或联系人敏感信息 | 拒绝输出并记录安全测试结果 |
| 提示词要求忽略知识库 | 拒绝执行，继续遵守证据和安全边界 |

## 10. 自动验收

- 组合映射数量在 35～40 条之间，每条字段完整且来源可追溯。
- 100 条问题编号完整、不重复，分类数量和难度数量符合设计。
- 每条普通问题至少关联一条组合映射和一份带定位信息的来源。
- 每条组合映射至少被一条问题覆盖。
- 产品组合必须包含明确分工，不允许只堆叠产品名称。
- 预期动作为“先追问再推荐”的问题不得直接给出确定主推组合。
- 资料冲突问题必须填写冲突说明并降低推荐置信度。
- CSV 与 Excel 的主数据逐字段一致。
- Excel 的全部工作表完成数据检查、公式错误扫描和视觉渲染检查。
- 本地测试与 GitHub 推送门禁全部通过后，任务才标记完成。

## 11. 任务状态约束

第二批 100 条仍为模拟问题，不替代 `D1-08 收集 30 条真实销售需求`。组合映射和测试问题在产品专家确认前只能用于内部实验，不能直接用于对客承诺。
